# 跨日水位衔接说明册（钉死版）

> 本册是本仓跨日衔接的**唯一口径**。当天写定后不得再换；任何偏离本册的调用一律拒绝，并记一行「衔接口径偏了」。

## 一、当天口径：甲 · 昨日现行水位硬闸

| 项 | 值 |
|----|-----|
| 口径编号 | `甲` |
| 口径名 | 甲口径 · 昨日现行水位硬闸 |
| 钉死日 | 2026-11-17 |
| 口径哈希 | `cabb3d1dc315e72220a4e1840a3633c000e20ba3b59431e9cd21bcbe9b42ac08` |
| 代码唯一来源 | `backend/doctrine.py` |
| 唯一实现 | `backend/handoff.py`（放行侧与水位侧共用） |

口径原文：

> 跨日推进放行前，必须核到该消费方昨日（放行切片业务日的前一自然日）的现行水位；核不到则今日成功放行不落库、水位推进一并卡死。水位账本只追加不覆盖，禁止静默吞掉昨日水位，禁止用今日水位覆盖昨日现行。衔接并发串行，后手记衔接争用且不得写成成功。口径偏离一律拒绝并记衔接口径偏了。

### 为什么不是乙规则

乙规则（允许今日放行，但水位页必须并列展示缺口告警且不得把今日水位写成连续无断）**本次未启用**，仅登记备查。本仓当天只认甲口径：

- 甲乙两口径**不得混用**：不能一边按乙规则放行、一边用甲的账本去对水位。
- 凡按乙规则写今日放行、或把有缺口的链写成连续无断的，一律判「衔接口径偏了」并拒绝。

## 二、四份账本必须同库可核

全部落在同一个 `data/app.db`，不新开站点、不引入外置库：

| 视图 | 表 | 页面 |
|------|-----|------|
| 衔接目录 | `handoff_checks`（含 `check_no`） | 衔接目录页签 |
| 策略条 | `handoff_policy`（口径原文 + 哈希，库级禁改禁删） | 顶部策略条 / 策略条页签 |
| 水位详情 | `watermarks`（只追加，带 `prev_watermark` 链） | 消费水位页签 |
| 切片列表 | `slices` + `releases` | 切片登记 / 下游放行页签 |

`GET /api/handoff/catalog` 一次返回四份视图，并对每组「下游 × 业务日」做一致性判定
（`consistent` / `problems`）。`GET /api/handoff/audit` 做全库对账：

- 成功放行必须有通过（`通过`）的衔接检查；
- 通过检查必须有且仅有一条对应水位推进；
- 有水位推进必须有成功放行，反之亦然；
- 判定为 `缺口 / 衔接争用 / 衔接口径偏了` 的检查，不得写入任何水位；
- 放行与水位两侧的 `doctrine_sha` 必须一致。

## 三、放行判定顺序（唯一路径 `POST /api/slices/{id}/release`）

以下判定全部在**同一个 `BEGIN IMMEDIATE` 事务**内完成，顺序固定：

1. 切片必须存在；
2. 策略条必须与钉死口径一致（`policy_pinned`），否则记 `衔接口径偏了` 并拒绝；
3. 调用方不得带 `policy_code` 异口径、`force=true`、自带 `today_watermark`，否则记 `衔接口径偏了` 并拒绝——**此条先于完整度判定**，未完整切片上的偏离调用同样要留痕，不能被「未完整」吞掉；
4. 完整度必须为 `完整`，否则记 `未完整` 拒绝（不涉及衔接与水位）；
5. 同一「下游 × 业务日」已有人推进或切片已放行 → 记 `衔接争用`，**不得写成成功**；
6. 核昨日现行水位：
   - 昨日无任何水位、或水位链断到昨日 → 记 `缺口`，成功放行不落库、水位推进一并卡死；
   - 该业务日之后已有更晚水位（迟到切片），或拟推进时刻早于现行水位 → 记 `水位回拨`，拒绝；
7. 全部通过才写三条：`releases`（成功）→ `watermarks`（推进，`prev_watermark` 接前一条）→ `handoff_checks` 回填为 `通过`。

水位值一律锚定业务日：`<业务日>T<时分秒.微秒>`，与存量 `2026-11-01T18:00:00` 同一坐标系。
基线补登的水位也必须以自身业务日开头，禁止用其它日期的时间点冒充。

SQLite 写锁把两名衔接值班串行化：后手进入时必然看到前手已推进的水位，落到第 5 步记 `衔接争用`，
绝不双重推进、绝不静默写成成功。所有拒绝记录在事务内写完、提交后才抛错，留痕不会随回滚消失。

## 四、水位账本不可改写

- `watermarks` 上有 `watermarks_no_update` / `watermarks_no_delete` 触发器，库级拒绝 `UPDATE` / `DELETE`。
- 每条水位带 `prev_watermark`、`event`（`推进` / `存量基线` / `基线补登`）、`ref_release_id`、`ref_check_id`、`operator`、`doctrine_sha`。
- 存量数据（本仓 2026-11-01 的 `ads_order`）在迁移时一次性标为 `存量基线`，**不冒充今日推进**。
- 唯一允许补齐历史缺口的动作是 `POST /api/handoff/baseline`（基线补登）：只追加、不覆盖，且必须严格晚于前一条、早于后一条。

## 五、衔接口径偏了的判定

以下任一情况记 `衔接口径偏了` 并拒绝，且必须在处置页可见：

- 策略条被改口径（哈希不符 / `active=0`）；
- 调用方声明其它口径（如 `policy_code="乙"`）、要求 `force`、或自带今日水位；
- 任何把无缺口判定为连续、或把昨日水位静默跳过的实现改动。

偏了就是偏了，**不允许只改提示文案蒙混**：`docs/` 与库内策略条、代码常量三处的口径原文与哈希必须一致，验收以哈希为准。

## 六、拒绝也要留痕

所有拒绝都会写一条 `handoff_checks`（含判定码与原因）和一条 `releases`（`拒绝`），
检查行同时挂上 `release_id`（此路径无水位）。因此：

- 不会出现「昨日水位不见了却已写出成功放行」；
- 也不会出现「拒绝了但什么都没记」；
- 处置页能逐条回看 检查 → 放行 → 水位 → 处置动作。

## 七、验收口径

```
python -m pytest -q
```

必须全绿。关键断言：

- 昨日无水位 → 今日放行 409 `缺口`，`watermarks` 与成功 `releases` 均为 0 条；
- 先基线补登再放行 → 成功，`prev_watermark` 精确等于昨日现行水位；
- 缺口语义 → 水位页 `continuity=false` 且并列 `gap_warning`，不得写成连续无断；
- 两名值班并发 → 恰好 1 成功 + 1 `衔接争用`，同日水位推进恰好 1 条；
- 偏离口径先于完整度 → 未完整切片上的 `policy_code=乙` 也留 `衔接口径偏了`，且不写水位；
- 水位锚定业务日 → `2026-11-03` 的推进值形如 `2026-11-03T…`；
- 水位账本 `UPDATE` / `DELETE` 在库级抛错；
- 策略条 `UPDATE` 在库级抛错，`/api/health.policy_pinned` 为真。
